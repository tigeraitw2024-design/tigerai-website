# 後台架構

一句話：**後台是一份「欄位定義」，其他東西都是從它長出來的。**

## 為什麼這樣設計

Robin 的要求是「每一個功能都是一個元件」。真正做到這件事，不能只是把檔案分資料夾，
而是要讓「新增一個功能」這件事只需要寫一個檔案，不用去改後台介面、不用改 API、
不用寫 SQL。所以這裡的做法是：

```
src/api/modules/courses.ts   ← 只寫這一個檔
        ↓
    自動長出  資料表、列表頁、編輯表單、權限、API、匯出
```

一個模組檔就是一個功能元件。刪掉它，那個功能就整個消失，不會在別處留下殘骸。

## 三層

```
  src/api/schema/      欄位型別與集合定義（是什麼）
  src/api/modules/     每個功能一個檔（有哪些）
  src/api/routes/      泛用 CRUD，照著 schema 跑（怎麼存取）
  src/admin/           後台介面，跟 /api/schema 要定義後自己畫出來（怎麼看）
```

後台介面**沒有**任何一頁是為某個功能手寫的。它問 API 拿到欄位定義，就知道
「課程有一個叫 price 的欄位、型別是金額、必填」，然後畫出對應的輸入框。
所以加欄位＝改一行 schema，後台當場就有。

## 內容怎麼到前台

前台是靜態的（`output: 'static'`），這是它能 0.00% 對上原型、又不吃 Cloudflare
免費方案每次請求 10 毫秒運算額度的原因。所以內容不是「前台去資料庫拿」，而是：

```
  後台編輯 → 存進 D1 → 按「發布」→ 觸發重新建置 → 靜態檔重發
```

建置時 `src/content/` 會去 D1 把內容抓下來烤進 HTML。**抓不到就用
`src/data/*.ts` 的本地資料**（現在站上跑的就是這份）。這條退路很重要：
資料庫還沒開、網路不通、或在別人的電腦上，站都照樣建得起來，而且建出來
跟現在一模一樣，像素驗證不會因為後台而破。

會跟著跑的東西（預約、名單、會員、訂單、購物車）本來就必須即時，
那些走真正的 API，不烤進靜態檔。

## 集合的兩種性質

| kind | 意思 | 例子 | 前台怎麼拿 |
|---|---|---|---|
| `content` | 編輯後要重新發布才上線 | 課程、產品、顧問、案例、文章 | build 時烤進去 |
| `runtime` | 隨時在變，即時讀寫 | 預約、名單、會員、訂單 | 前台呼叫 API |
| `singleton` | 只有一筆 | 全站設定、首頁各區文案 | build 時烤進去 |

## 可抽換的部分

Robin 的第二個要求：換金流、換寄信、換儲存，不用重寫網站。所以這三件事
都只透過介面呼叫，實作放在 `adapters/`，用環境變數選：

```
  adapters/mail/      寄信    console（印出來）｜ smtp-relay ｜ resend
  adapters/payment/   金流    none（只記單）｜ ecpay（綠界，等 Robin 給 API）
  adapters/storage/   檔案    r2 ｜ memory（本機測試）
```

換一家＝寫一個新檔案 ＋ 改一個環境變數。呼叫端完全不用動。

## 權限

後台帳號分四種角色，重點是**同事看不到客戶個資**：

| 角色 | 能做什麼 |
|---|---|
| `owner` | 全部，包含開帳號 |
| `editor` | 只有內容：課程、產品、顧問、案例、文章、設定。**看不到預約、名單、會員、訂單** |
| `sales` | 內容唯讀 ＋ 預約、名單、訂單（含聯絡方式） |
| `viewer` | 全部唯讀，且個資欄位一律遮成 ●●● |

欄位層級也有保護：schema 裡標了 `pii: true` 的欄位（電話、Email、公司），
沒有權限的人拿到的就是遮罩後的值，不是「前端不顯示」——是 API 根本不給。
